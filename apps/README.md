# Applications

Deployable application components live here, each with its own runtime dependencies and tests.

## `remittance-processor`

The Python Azure Functions app (Dedicated plan). A Service Bus-triggered starter (`function_app.py`) begins one **Durable Functions** orchestration per intake message (`orchestration/orchestrator.py`, instance id = `processingId`). Activities (`orchestration/activities.py`) call `msg_parser/` (MSG + `.eml` decomposition, candidate scoring, manifest), `extraction/` and `validation/` (merge, dedupe, reconciliation, CSV). `extraction/` holds the self-verifying table readers for the email body (`html_tables.py`, `text_tables.py`), the deterministic spreadsheet parser, and Content Understanding (429/5xx backoff, chunking with an overlap-aware merge, and `ground_lines`, which flags any PRO/amount pair not found together in the source). Review runs go through `assurance/`: `triage.py` splits them into extraction, data-quality and payer issues; `case.py` sends only the payer issues, with their exact lines, to the ACH Assurance Expert (`ach-assurance-expert`; `experts.py` via `shared/foundry_agents.py`). Table column mapping is done by the ACH Extraction Expert (`ach-extraction-expert`, `extraction/column_mapping.py`), with the original header rules as a frozen fallback; `fusion.py` returns one finding per issue and picks the primary one. `shared/recorder.py` is the single writer of the ledger + events tables and audit blobs. `function_app.py`, `host.json` and `requirements.txt` stay at the component root because it is the Functions deployment root.

## `api`

FastAPI backend (Container App, internal ingress). Upload writes `incoming/{processingId}/{name}` and sends a claim-check message to the Service Bus intake queue; it never writes governed run state. Until the Function's first ledger write, run detail returns a read-only `Queued` placeholder derived from the source blob, not a 404. Reads: run list/detail, live events, artifacts (download scoped to the run's `processingId`), CSV, pipeline status (queue depth, in-flight by stage, throughput) and daily/weekly summaries with a by-payer roll-up; actions: reprocess and dead-letter replay. Ledger access is behind `LedgerRepository` so the store can later be swapped (Table → Cosmos) with no UI change. Pure transforms live in `app/transforms.py` and are unit-tested.

## `ui`

React + Vite single-page app (Fluent UI, Recharts) served by nginx, which reverse-proxies `/api` to the `api` app. Pages: **File Upload** dashboard (multi-file upload, live workflow tracking, live pipeline card, recent files, runs needing review), **Live Pipeline** (queue/DLQ, throughput, in-flight runs), **Processing Runs / Exceptions / Audit** (searchable lists), **Run Details** (summary, review reasons, one assurance card per finding with its owner, action, affected lines and policy citations, payment lines, sources, files, live timeline; list views show the primary finding as a pill), and **Summaries** (daily/weekly KPIs, agent decisions, by payer). Near-real-time updates use polling (2-3 s while work is in flight). `node_modules`/`dist` are gitignored and excluded from the image via `.dockerignore` (patterns must have **no trailing slash** for `az acr build`).
